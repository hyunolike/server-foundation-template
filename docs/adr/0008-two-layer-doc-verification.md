# 0008. 문서 검증을 두 겹으로 나눈다

- 상태: 수용됨
- 관련: [설계 문서 §7.4](../design/architecture.md)

## 맥락

"REST Docs를 쓰면 문서와 실제 응답이 일치한다"는 말은 정확하지 않다. REST Docs가 보장하는 것은 **자기 스니펫에 적은 필드가 실제 응답에 있다**는 것뿐이고, springdoc이 만든 `openapi.json`의 존재조차 모른다. 두 도구를 섞어 쓰면서 이 차이를 뭉개면, 검증하고 있다고 믿으면서 아무것도 검증하지 않게 된다.

## 결정

검증을 두 겹으로 명시적으로 나눈다.

| 겹 | 도구 | 보장하는 것 |
| --- | --- | --- |
| 예시의 실재성 | Spring REST Docs | 문서의 예시·필드 설명이 실제 테스트가 받아 낸 응답에서 나왔다 |
| 스펙 일치 | OpenAPI 응답 검증기 | 실제 응답이 생성된 `openapi.json`의 해당 스키마를 만족한다 |

## 결과

- 둘 다 "테스트가 있는 엔드포인트"만 본다. 커버리지는 테스트 커버리지와 같다.
- 첫 번째 겹은 응답에 없는 필드를 문서에 적어도, 있는 필드를 빠뜨려도 깨진다.
- 두 번째 겹은 커스터마이저가 봉투를 잘못 주입했을 때 잡는다.
- 셋째 게이트인 스냅샷 검증([0004](0004-commit-openapi-json.md))은 성격이 다르다 — 스펙이 맞는지가 아니라 갱신을 잊었는지를 본다.
