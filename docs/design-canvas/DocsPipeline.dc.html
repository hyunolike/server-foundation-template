DOCUMENTATION PIPELINE
표준화가 곧 문서가 되는 지점
봉투를 Advice에서 씌우면 컨트롤러 시그니처만 보는 springdoc은 거짓 문서를 만든다. 이 템플릿의 핵심은 그 간극을 커스터마이저로 메우고, 테스트로 검증하는 것이다.
STEP 1
작성
컨트롤러에 @Operation과 @ApiErrorCodes만 단다. 응답 스키마는 적지 않는다.
STEP 2
생성
springdoc이 스펙을 뽑고, 커스터마이저가 봉투 스키마와 에러 응답을 주입한다.
STEP 3
검증
REST Docs 테스트가 실제 응답으로 스니펫을 만든다. 문서와 응답이 다르면 테스트가 깨진다.
STEP 4
발행
openapi.json을 커밋하고 정적 문서를 배포한다. 스펙 변경은 PR diff에 남는다.
개발자가 쓰는 것
@Tag(name = "User") @RestController @RequestMapping("/api/v1/users") class UserController( private val userService: UserService, ) { @Operation(summary = "사용자 단건 조회") @ApiErrorCodes(USER_NOT_FOUND) @GetMapping("/{userId}") fun get(@PathVariable userId: Long): UserResponse = userService.get(userId) // 봉투도, 에러 스키마도 쓰지 않는다. // 둘 다 파운데이션이 채운다. }
문서에 나타나는 것
/api/v1/users/{userId}: get: summary: 사용자 단건 조회 responses: '200': schema: ApiResponse<UserResponse> ← 주입 headers: [ X-Trace-Id ] ← 주입 '404': code: USER_NOT_FOUND ← 주입 description: 사용자를 찾을 수 없습니다. schema: ApiErrorResponse '500': code: COMMON_INTERNAL_ERROR ← 전역 기본 schema: ApiErrorResponse
자동으로 채워진다
봉투 래핑 스키마 ApiResponse<T>와 meta 필드
에러 코드 목록 → 상태별 응답 (코드 · 메시지 · 스키마)
공통 응답 헤더 X-Trace-Id
페이징 쿼리 파라미터와 PageResponse 스키마
전역 기본 응답 (400 · 401 · 500)
사람이 써야 한다
엔드포인트 요약과 “언제 쓰는가” 설명
의미 있는 요청·응답 예시 값
도메인 용어 정의 (docs/glossary.md)
인증 방식과 권한 요구사항
결정의 배경 — ADR에 남긴다
CI 게이트 — 문서가 낡으면 빌드가 막는다
gradle test
REST Docs 스니펫은 테스트가 통과해야 나온다. 문서 조각이 없으면 문서 빌드가 실패한다.
openapi:verify
스펙을 다시 생성해 커밋된 openapi.json과 비교한다. 차이가 있으면 실패 — 갱신 누락을 막는다.
openapi:diff
기준 브랜치와 비교해 필드 삭제 · 타입 변경 · 에러 코드 제거를 찾아 PR에 코멘트로 남긴다.
