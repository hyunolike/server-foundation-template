ARCHITECTURE DESIGN · DRAFT v0.1
server-foundation-template
문서화와 요청·응답 표준화를 하나의 계약으로 묶은 Kotlin · Spring Boot 서버 파운데이션. 새 서비스는 이 템플릿을 복제해 도메인 코드부터 쓰기 시작한다.
Kotlin 2.x
Spring Boot 3.x
JDK 21
Gradle Kotlin DSL
01 — 설계 원칙
봉투는 경계에서만
컨트롤러는 도메인 DTO를 그대로 반환한다. ResponseBodyAdvice 한 곳에서만 표준 응답으로 감싸므로, 서비스 계층에 응답 규격이 새어 들어가지 않는다.
에러 코드는 한 곳에서
ErrorCode가 코드 · HTTP 상태 · 메시지 키를 함께 들고 있다. 런타임 응답, OpenAPI 문서, 계약 테스트가 전부 이 레지스트리 하나를 읽는다.
문서는 생성하고 검증한다
springdoc이 코드에서 OpenAPI를 뽑고, 스펙 응답 검증기가 실제 응답을 그 스펙에 대조한다. 문서를 손으로 고쳐 맞추는 일이 생기지 않는다.

03 — 기술 선택과 근거
영역
선택
근거
웹 스택
Spring Web MVC
Filter / Interceptor / Advice 훅이 표준화의 핵심이다. WebFlux는 이 훅 구성이 달라 범위에서 제외.
직렬화
Jackson + module-kotlin
springdoc의 스키마 추론이 Jackson 기준이다. kotlinx.serialization은 문서 자동화와 충돌.
API 문서
springdoc-openapi 2.x
코드 우선 생성. 봉투 래핑은 OpenApiCustomizer로 문서에 되돌려 넣는다.
문서 검증
REST Docs + 스펙 응답 검증
REST Docs는 예시가 실재함을, 응답 검증기는 실제 응답이 생성된 스펙을 만족함을 보증한다.
빌드
Gradle KTS + 버전 카탈로그
멀티모듈 의존성을 libs.versions.toml 한 파일에서 고정.
관측성
Micrometer + Logback JSON
traceId를 응답 meta, 응답 헤더, 로그에서 같은 이름으로 쓴다.
